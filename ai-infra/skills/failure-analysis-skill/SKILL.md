# failure-analysis-skill — 故障分析与阻断

## 适用场景

- 同一错误签名失败 2 次
- 测试结果与预期不一致且无法解释
- 管道、浏览器、GUI 自动化行为不稳定
- 连续重试无进展
- GPT-5.5 复核指出 P0/P1 但无法修复
- 复杂、重复、跨组件、无法解释或高风险的技术问题：测试失败、生产 bug、性能问题、构建失败、集成问题（简单 typo、明确语法错误、普通格式问题不必强制进入完整故障流程）

## 核心铁律

```
未完成根因调查之前，不得提出修复方案。
修复症状不是修复 bug。随机补丁浪费时间和制造新 bug。
违反此流程的字面规定即违反调试精神。
```

**紧急情况尤须遵守：** 压力下最容易走捷径。看上去"只是一个快速修复"的东西恰恰是最需要走流程的。

## same_error_signature 定义

满足以下任意 3 项，即视为同一错误签名：

- 错误码相同
- 失败阶段相同
- 关键日志相同或高度相似
- 测试名相同
- 失败文件/函数相同
- 外部现象相同
- 用户目标未变化

以下不算换策略：

- 只改 timeout
- 只重启或重跑
- 只增加重试次数
- 只清缓存但没有新证据
- 只换 selector 但未验证 DOM/截图
- 只改提示词措辞但执行路径相同

## 安全分级约束

调查和修复期间同样受 L0-L5 限制：

- 读取普通源码、普通日志：L0
- 新增最小复现测试、诊断日志、非敏感报告：L1
- 修改配置、启动脚本、队列协议、测试策略：L2，需计划
- 删除、覆盖、move、kill、桌面点击、安装依赖：L3，必须 dry-run + 人类确认
- exec、SSH、凭据、浏览器 profile、端口暴露、artifact 下载逻辑：L4，必须 GPT-5.5 复核 + 人类确认
- 生产环境、批量删除、凭据轮换、公开网络暴露：L5，默认禁止

**调查阶段不得为了收集证据读取 secrets、cookie、SSH key、浏览器 profile、.env；确需读取时至少按 L4 处理。**

## 四阶段流程

必须完成当前阶段再进入下一阶段。不得跳过。允许提出根因假设，但必须标记为"假设"，不得在证据不足时执行修复。

### 第一阶段：根因调查

**在提出任何修复之前：**

1. **仔细阅读错误信息**
   - 不跳过错误或警告
   - 错误信息常常包含精确答案
   - 完整阅读堆栈回溯
   - 记录行号、文件路径、错误码

2. **稳定复现**
   - 能否可靠触发？
   - 精确步骤是什么？
   - 每次都发生？
   - 不可复现 → 收集更多数据，不猜测

3. **检查最近变更**
   - 什么变更可能导致这个？
   - Git diff、最近 commit
   - 新依赖、配置变更
   - 环境差异

4. **多组件系统中的证据收集**
   当系统有多个组件（pipeline → server → queue → browser → relay）时：
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 记录组件内部状态
     - 定位哪个组件是故障源
   ```
   在定位故障组件之前，不要提出修复——修复可能在错误的组件中。

### 第二阶段：根因追踪

1. **观察症状**：具体发生了什么？
2. **定位直接原因**：哪段代码直接导致？
3. **向上追踪**：谁调用了它？传了什么参数？
4. **继续追踪**：参数从哪里来？一直到原始触发器
5. **定位根因**：原始触发器是什么？为什么产生错误值？

原则：在调用链中向后追踪，直到找到原始触发器，然后在源头修复。在错误出现的地方修复只是治疗症状。

### 第三阶段：最小验证

1. 先写能复现问题的最小测试
2. 如果无法写自动化测试，必须给出最小手工复现步骤、截图/日志采集点和通过/失败判据
3. 不得直接在生产路径上验证；先在隔离环境、测试样例或 dry-run 中验证
4. 确认在修复前测试失败
5. 应用最小修复
6. 确认测试通过
7. 确保没有引入新问题

对于多组件系统：追踪每个组件边界的数据流动。只有在修复前添加诊断插桩确认了故障组件，才在那个组件中修复。

### 第四阶段：防御加固

只修根因还不够。考虑：

- 为什么根因最初会被触发？
- 错误发生位置能否更好的错误处理？
- 能否在组件的边界尽早捕获无效输入？
- 修复后需要什么回归测试来防止回退？
- 对跨组件系统，修复后必须在故障源上游边界增加断言、校验或清晰错误信息，避免错误值继续向下游传播




## 禁止行为

- 不允许第三次原样重试
- 不允许只改参数不换策略
- 不允许没有新证据就宣布修复
- 不允许在无截图的 GUI 操作失败后继续盲打
- 不允许用"这次应该可以"代替根因分析
- 不允许 agent 自行升级到 L3+ 操作规避失败
- 不允许未完成根因调查就提出修复。必须至少完成根因追踪（第二阶段）和最小验证计划（第三阶段）后方可提出修复方案。防御加固（第四阶段）是关闭故障报告前的必需步骤。
- 允许提出根因假设，但必须标记为"假设"，不得在证据不足时执行修复

## 验证步骤

1. 确认前两次失败是否满足 same_error_signature
2. 是否完成了四阶段中的前三个阶段
3. 新方案与前两次有本质区别
4. 将脱敏故障报告发给 GPT-5.5 复核
5. 新方案先做最小验证
6. 通过后再扩大范围
7. 记录到任务报告

## 失败停止条件

- 已刹车 2 次 → 暂停任务方向，GPT-5.5 重新评估
- 无法找到根因 → 生成最小复现用例
- 未完成根因调查 → 不得提出修复
- 需要 L3+ 操作 → 必须人类确认
- 涉及 P0/P1 风险 → 先修风险，不继续业务目标
